## Context

`frontend/` 自 v1 起存在且為空——v1 明確決定不做前端 UI，理由是這個專案的價值在
訊息路徑、配置演算法與併發正確性，不在介面。`add-demo-console-api` 提供了六支端點
之後，缺的只剩一個能讓人在螢幕分享時跟得上的操作介面。

這個應用的使用情境很窄：本機、桌面瀏覽器、由開發者本人操作並口頭解說。它不需要
部署、不需要多使用者、不需要行動版面。這個窄範圍是後續多數設計決定的依據。

本 repo 目前是純 Gradle 專案，沒有任何 Node 工具鏈。本次引入的 `frontend/` 是一個
獨立的 Node 專案，不與 Gradle build 整合。

後端的非同步性質會直接影響介面：`POST /demo/replenish` 回 `202`，配置結果只能由
後續查詢觀察。介面必須誠實反映這件事，不能讓觸發補貨看起來像配置已完成。

## Goals / Non-Goals

**Goals:**

- 讓下單、查最近訂單、查庫存、觸發補貨四件事可在瀏覽器完成。
- 讓觀看者能看出目前跑的是 v1 還是 v3 分區策略。
- 讓非同步的配置結果在介面上被誠實表達，不製造「已完成」的錯覺。
- 讓所有資料取得可追溯到明確的使用者動作，沒有背景活動。
- 後端零改動——CORS 不進後端程式碼。

**Non-Goals:**

- 不做登入、權限、多使用者。
- 不做篩選、排序切換、真分頁。
- 不做取消訂單按鈕。
- 不做輪詢、WebSocket、SSE 或任何自動更新。
- 不做 production build、容器化、部署。
- 不做行動裝置版面。
- 不做訂單詳細頁或 modal，也不呈現事件因果鏈——後端不提供，列表已含全部欄位。
- 不引入元件庫或設計系統，不追求視覺打磨。
- 不改動任何後端程式碼或合約。

## Decisions

### 兩頁一個 router，且沒有訂單詳細檢視

四個功能不對應四頁。「下單 → 看它出現在列表」與「查庫存 → 補貨 → 再查一次確認」
各自是連續動作，拆成獨立頁面會讓單次操作跨頁跳轉。因此收斂為訂單頁與庫存頁兩頁，
兩頁之間有真正的導覽需求，router 不是為分而分。

不做訂單詳細檢視（不論是第三個路由或 modal）。訂單表示只有八個欄位，列表那一列
就全部顯示得下；點開一個只為了看同樣欄位的視圖，是同一份資料的第二次呈現。原本規劃
的詳細 modal 是為了容納事件因果鏈，而該功能已從 `add-demo-console-api` 移除——outbox
記錄的是「本服務對外發布了什麼」，不是「這張訂單發生了什麼」，不是訂單歷史的正確
來源。

考慮過單頁加三個 popup（列表佔滿主體，下單與 SKU 面板各自開 modal）。它避免引入
router，但把所有操作入口藏在按鈕之後，而這個介面的用途正是讓觀看者一眼看出系統
提供哪些操作。

### 以 Vite dev proxy 取代後端 CORS 設定

前端在 dev server 的 origin 上以同源路徑呼叫後端，由 dev server 轉發。瀏覽器不發生
跨來源請求，後端因此不需要任何 CORS 設定。

替代方案是在後端加一個 dev profile 限定的 CORS bean。它可行，但會在後端程式碼裡
留下一個只為前端存在的組態，而寬鬆的 CORS 設定一旦存在就有被複製到其他 profile
的風險。把這件事完全留在前端工具鏈裡，後端保持零改動。

後端 origin 只出現在 dev server 設定中，不出現在應用程式原始碼——原始碼一律使用
相對路徑，因此換後端位址不需要改任何元件。

### 不輪詢：所有取數由使用者動作觸發

沒有計時器、沒有背景刷新、沒有 WebSocket。每次請求都對應一個動作：進入頁面、送出
表單、按查詢、按重新整理。

這讓整個應用不需要處理輪詢帶來的一整類問題——請求競態、頁面隱藏時的空轉、多個
in-flight 請求的順序、卸載後的狀態更新。代價是使用者必須自己按重新整理才看得到
非同步配置的結果，而這個代價在「由操作者本人邊操作邊解說」的情境下幾乎不存在，
反而讓「補貨是非同步的」這件事在操作上顯而易見。

訂單頁因此必須有明確的重新整理控制項——列表在後端完成非同步配置後就過時了，
沒有這個控制項，使用者只能重新載入整頁。

### 手寫 TypeScript 契約型別，不引入 OpenAPI 產生器

後端目前沒有 OpenAPI 文件，要產生型別得先在後端加入文件產生器，那會把
`add-demo-console-api` 的範圍撐大。

改為在單一模組中手寫對應六支端點的型別，並在該模組註明它是唯一需要跟隨後端合約
變動的地方。這是刻意的取捨而非疏漏：型別與後端不同步時，錯誤會出現在執行期而非
編譯期。範圍夠小（六支端點、兩個主要資料形狀）使這個風險可控。

### 不引入資料抓取函式庫，以單一 async 動作 hook 統一 loading 與 error

沒有輪詢、沒有快取需求、沒有跨頁共享的伺服器狀態，資料抓取函式庫的主要價值在此
不成立。

但六個動作各自複製一份 loading／error／result 的狀態機會製造重複，也容易讓某個
動作漏掉錯誤處理。因此定義一個泛型的 async 動作 hook，統一三種狀態的表達，讓
「失敗必須被呈現」成為結構上的預設而非每處自律。

### 前端測試聚焦於有邏輯的部分

不對純版面元件寫測試。測試對象是兩處實際含有邏輯的地方：下單表單的提交前驗證
（非正整數與空 SKU 不得送出請求），以及失敗路徑（動作失敗時錯誤被呈現且不顯示成功
跡象）。

這兩處正是規格中以行為描述、且容易在後續修改中被破壞的部分；版面則不是。

## Implementation Contract

**Behavior:**

- 根路徑進入訂單頁。訂單頁含下單表單、最近訂單列表與重新整理控制項；列表每一列
  攤開訂單表示的全部欄位，沒有詳細檢視。
- 庫存頁含 SKU 查詢與補貨觸發，兩者針對同一個 SKU。
- 兩頁共用頁首，顯示由後端取得的目前分區策略，導覽時不重複請求。
- 補貨成功後顯示已受理與事件識別碼，並說明配置結果需再次查詢才能觀察；不顯示
  任何配置已完成的訊息。
- 未知 SKU 顯示明確的查無此 SKU 狀態。
- 任一動作失敗時顯示該動作失敗，且不保留看似成功的輸出。

**Interface / data shape:**

- 應用消費 `add-demo-console-api` 的六支端點，一律以相對路徑呼叫，經 dev server
  代理轉發至後端。
- 型別定義集中於單一模組，涵蓋訂單表示、庫存狀態、補貨受理回應與組態回應。

**Failure modes:**

- 後端不可用、`404`、`5xx` 皆由發起該動作的區塊就地呈現，不使用全域錯誤橫幅
  掩蓋來源。
- 表單在送出前阻擋非正整數數量與空 SKU，此情況不發出請求。
- 補貨失敗時不顯示事件識別碼。

**Acceptance criteria:**

1. 元件測試驗證：數量為 0、負數或 SKU 為空時，表單不發出請求。
2. 元件測試驗證：動作失敗時該區塊顯示失敗，且畫面上不存在成功跡象（補貨失敗時
   無事件識別碼）。
3. 手動驗收：`npm run dev` 啟動後，在後端 dev profile 執行中的情況下完成完整劇本
   ——下單並在列表看到 `PENDING`；查一個 ATP 為 0 且有 backorder 佇列的 SKU；
   對其補貨並看到已受理與事件識別碼；回訂單頁按重新整理，看到該批訂單轉為
   `ALLOCATED` 且列上的 `allocatedAt` 有值。
4. 手動驗收：頁首顯示的分區策略與後端啟動時的設定一致，`order-id` 與 `sku` 兩種
   設定各驗證一次。
5. 手動驗收：訂單頁載入完成後靜置，瀏覽器開發者工具的網路面板不再出現新請求。

**Scope boundaries:** 涵蓋 `frontend/` 下的 Node 專案、兩個頁面、共用頁首、型別模組、
async 動作 hook、dev proxy 設定、元件測試與 `frontend/README.md`。不涵蓋任何後端
程式碼、訂單詳細檢視、production build、部署、Gradle 整合、自動更新機制、行動版面，
以及 `add-demo-console-api` 已涵蓋的端點行為。

## Risks / Trade-offs

- [手寫型別與後端合約不同步，錯誤延後到執行期才出現] → 型別集中於單一模組並註明
  其與後端合約的對應關係；範圍限於六支端點，使人工同步可行。若端點數量成長，
  再評估在後端引入 OpenAPI 文件產生器。
- [不輪詢使得非同步配置結果需要手動重新整理，可能被誤認為系統沒反應] → 補貨受理
  後明確說明結果需再次查詢才能觀察；訂單頁提供明確的重新整理控制項。
- [首次引入 Node 工具鏈，增加 repo 的維護面] → 不與 Gradle 整合，兩套工具鏈各自
  獨立；前端不參與後端的建置或測試流程，後端也不依賴前端存在。
- [列表一列攤開八個欄位導致橫向過寬、難讀] → 這是刻意取捨，換得「不需要第二層
  檢視」；若寬度成為實際問題，先精簡顯示的時間戳（未發生的階段留白），而不是重新
  引入詳細檢視。

## Migration Plan

1. 先完成 `add-demo-console-api`——本應用沒有它就沒有可用的後端合約。
2. 在 `frontend/` 建立 Vite React TypeScript 專案與 dev proxy 設定。
3. 實作型別模組、async 動作 hook、共用頁首與兩個頁面。
4. 補上元件測試並全數通過。
5. 啟動後端 dev profile 與前端 dev server，執行驗收劇本第 3 至 5 項。

回滾：本應用不影響後端執行，移除 `frontend/` 內容即回到現狀。
