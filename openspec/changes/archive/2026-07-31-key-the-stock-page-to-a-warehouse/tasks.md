## 1. 後端查詢

- [x] 1.1 依 `order-promising-http-api` 的 **Stock held in a warehouse is queryable by owner and warehouse**，`StockPoolRepository` 新增「某貨主某倉的全部批」的查詢，依 `(sku_code, expiry_date, in_date, id)` 排序。行為上：同一個 SKU 的批相鄰，且組內是 FEFO。以 SIT 驗證排序。

  排序由查詢保證而不是留給呼叫端：tie-break 一路排到 row identity，那個值存在的目的就是讓順序可重現，呼叫端手上沒有任何可以照它排的意義。

- [x] 1.2 `GetStockPoolUsecase` 改成收 `(ownerId, nodeId)`，**移除查無時丟 `NoSuchElementException`**。行為上：空倉回空清單而不是例外。以 controller 測試（HTTP 層回 200 空清單）與 SIT（repository 回空 map）驗證。

  空倉是正常答案，不是問了不存在的東西——而且那正是新倉上線時的狀態。

  原本寫「以單元測試驗證」，**改成由上下兩層驗**：移除例外之後這個 usecase 只剩一行委派，替它寫的單元測試會 stub 掉 repository 再斷言委派結果——那是在測 mock，不是測行為。真正會壞的兩個地方是 repository 回什麼、HTTP 回什麼，兩者都有測試。

- [x] 1.3 `StockPoolController` 改成 `GET /stock-pool?ownerId=&nodeId=`，回應依 SKU 分組。行為上：兩個參數缺一即 `400`；空倉回 `200` 與空清單。以 controller 測試涵蓋三種情形驗證。

- [x] 1.4 **不驗貨主–倉的指派關係**。行為上：未指派的組合回空清單而不是 `404`。以程式碼審閱驗證——`FulfillmentNodeRepository` 在 `catalog` 底下，讀它會讓 allocation 首次依賴 catalog。

- [x] 1.5 移除 `GET /stock-pool/{sku}`、`GetStockPoolUsecase` 的跨倉方法、`StockPoolRepository.findBatchesAcrossNodes`，以及它們的測試。行為上：`grep -r findBatchesAcrossNodes` 零命中。

  production 的呼叫端只有操作台一處。一支沒人呼叫的端點與它的 spec 要繼續維護，而兩支只差在查詢軸的庫存查詢會讓人每次都要想該用哪一支。

## 2. 前端資料層

- [x] 2.1 `api/client.ts` 的 `getStockPool` 改成收 `(ownerId, nodeId)`，型別跟著改。行為上：`tsc` 通過。

- [x] 2.2 把後端回的分組與主檔 left join 成完整列表：該貨主的**每一個**規格都有一列，倉裡沒有的四個數字都是 0、批是空的。以測試驗證「主檔有三個規格、倉裡只有一個有貨」時仍是三列。

  join 在前端做，因為 `allocation` 對 `archone.catalog` 零 import，而前端為了把代碼還原成看得懂的字本來就載了整份主檔。

  **實作時多加一個方向：列表是主檔與庫存的聯集，不只是主檔。** 有庫存卻查不到主檔的規格（壓測的 `HOT-SKU` 就是，`Catalog.skuCodesOf` 的註解已經記著這種貨存在）也要列出來，只是沒有品名、排在最後。漏掉它等於畫面上少報倉庫裡真實存在的貨。這一點 spec 沒寫到，見下方 5.5。

- [x] 2.3 依 `demo-console-frontend` 的 **On-hand SHALL include expired batches and available-to-promise SHALL NOT**，算出一列的四個數字。行為上：有過期批時在手 ≠ 已預留 ＋ 可承諾，差額等於已過期。以測試用 design 決策 8 那張表的三列驗證。

## 3. 列表

- [x] 3.1 查詢列改成貨主 → 倉別兩個下拉，倉別只列該貨主已指派的倉。行為上：換貨主時倉別清空。以測試驗證。

- [x] 3.2 一列一個規格，四個數量欄。依主檔順序（款 → 規格）排列，**不隨數量變動**。以測試驗證重查前後列的位置不變。

  補完貨要手動重查才看得到結果，所以排序一旦跟著數量走，你補的那一列就會跳走——而重查的整個目的就是看它變了什麼。

- [x] 3.3 每一列可展開成它的批，欄位與順序照後端回的不重排。行為上：展開後最早到期的在前。以測試驗證。

- [x] 3.4 空倉時仍然列出全部規格、全部 0、每一列都能補貨。以測試驗證。

## 4. 補貨視窗

- [x] 4.1 補貨鍵掛在規格那一列上，點開跳出視窗。貨主、倉別、規格唯讀顯示。行為上：這三個值不可能與被點的那一列矛盾。以測試驗證它們不是輸入元件。

- [x] 4.2 入庫日與效期**預帶該規格最近效期那一批**的值；零庫存的規格兩欄留空。行為上：不改直接送就是往現有的批加貨。以測試涵蓋「有批」與「無批」兩種情形驗證。

  預設值是在替使用者選意圖。預帶今天會讓每天都開一列新的，庫存散成一堆小批——`run.sh` 的註解明寫這正是壓測 fixture 刻意固定日期要避開的事。

  **實作時多加一個條件：跳過已過期的批。** 過期的批排在 FEFO 最前面，照抄第一批就會把貨補到一批配貨永遠取不到的列上——製造看不見的死庫存。改成取「最近效期、且還沒過期」的那一批，全部過期或一批都沒有時兩欄留空。design 決策 9 沒想到這個情形。

- [x] 4.3 任一日期或數量缺漏即擋下送出，不發請求。以測試驗證。

- [x] 4.4 送出後關視窗、**不自動重查**，列表上方出現「已受理」與重查鍵。行為上：送出後列上的數字不變，直到手動重查。以測試驗證送出後沒有第二次 `fetch`。

  補貨回 202——發布成功不代表配置完成。自動重查在本機通常快到看不出來，但慢的那一次畫面會說謊，而且分不出「還沒處理到」與「處理完了但數字真的沒變」。

## 5. 驗收

- [x] 5.1 用種子資料手動走一次：甲貨主北部倉的烏龍茶應該是在手 155、已預留 80、可承諾 50、已過期 25，展開四批且最早到期的在前。

- [x] 5.2 乙貨主南部倉：`SKU-AVAILABLE` 在手 50 可承諾 50 卻一件都沒被預留（R8 那張跨 SKU 的單卡在 `SKU-EMPTY`），`SKU-EMPTY` 四個數字都是 0。對 `SKU-EMPTY` 補一批、重查——兩張缺貨單應該一起被喚醒，而 `SKU-AVAILABLE` 的預留量跟著跳上去。

  這一條同時驗了「有貨卻不配」與「補貨會順帶喚醒佇列」，而後者正是不自動重查換來的東西：那一幕是你自己點出來的。

- [x] 5.5 spec 補上「有庫存但主檔查不到的規格仍要列出」。行為上：`demo-console-frontend` 那條 requirement 說得出這種列的樣子。
