## Context

R3 讓庫存分倉，R8 讓一張單跨多個 SKU。兩者合起來讓庫存頁現在的問法過時了：它問的是「一個
SKU 散在哪些倉」，而配貨從來不跨倉——每一次配貨都鎖在一個倉裡。畫面問的問題與系統做的決策
對不上。

這份文件記錄十個決定，以及每一個被否決的替代方案。

## Goals / Non-Goals

**Goals**

- 查詢軸改成 `(貨主, 倉別)`，列表以規格為單位、批為展開後的第二層
- 補貨從那一列進去，不再要求重填已知的三個維度
- 「有貨卻出不了」在聚合那一層仍然看得見

**Non-Goals**

- **不做輪詢或推播。** 補貨是 202，結果要重查。改成即時是另一個 change。
- **不動配貨。** 這是唯讀查詢加一支既有的 demo 探針，配貨路徑一行不改。
- **不做跨倉檢視。** 舊端點答得出「一個 SKU 在所有倉的分布」，但沒有畫面問這個問題（見決策 6）。

## Decisions

### 1. 一列一個規格，可展開看批

**否決：一列一個批（現狀粒度，只換查詢軸）。** 改動最小，但那不是貨品列表——同一個規格會
出現四次，而「這個規格總共還能出幾件」仍然要心算。

**否決：一列一個規格，完全不顯示批。** 最簡潔，但 FEFO 順序與「有貨卻過期」從畫面上消失。
`frontend/README.md` 把這兩件事寫成這一頁的存在理由：**順序就是配貨會取用的順序**，而過期的
批要列出來並標記，因為「有 100 件但一件都出不了」與「什麼都沒有」引導出不同的動作。

展開這一層違反了訂單頁定下的「不做點開看詳細，那會是同一份資料的第二次呈現」。**這裡不同：
一個規格的列真的裝不下 N 批**，不是同一份資料呈現兩次，是兩個層級。

### 2. 列出該貨主的全部規格，這個倉沒有的顯示 0

**否決：只列這個倉有庫存列的規格。** 那會讓這個倉從未放過的貨品再也進不去——而現在的表單
補得了（SKU 欄是 `skuCodesOf(ownerId)` 的 datalist，不限有庫存的）。這是功能倒退。

**否決：只列有庫存的，另加一顆「補新貨品」按鈕。** 補回了能力，代價是補貨有兩個入口、兩種
視窗，而其中一種要多一個規格欄。

零那幾列本身就是答案：**這個倉替這個貨主缺什麼。**

### 3. 補貨視窗的貨主、倉別、規格唯讀

**否決：倉別可改（原始構想）。** 查詢已經選了倉別，視窗再選一次就會出現一個矛盾狀態——你
點的是北部倉那一列，寫進去的是中部倉。送出後列表不會動，而畫面沒有任何東西解釋為什麼。

**否決：三者完全不出現。** 最乾淨，但「這一次補貨寫進哪一列」得從畫面別處推。README 強調
補貨要五個維度全填，正是為了擋掉這種推測——唯讀顯示讓五個都看得到，同時讓其中三個不可能
與你點的那一列矛盾。

要補別的倉：把上面的倉別下拉換掉，一步。

### 4. 送出後關視窗、不自動重查

`POST /demo/replenish` 回 **202**，Javadoc 明寫「發布成功不代表配置完成，配置結果只能由後續
查詢觀察」——它只等 broker ack，庫存變更走 Kafka consumer。

**否決：關視窗後立刻自動重查。** 本機通常快到看不出來，但慢的那一次畫面會說謊，而且你分不
出「還沒處理到」與「處理完了但數字真的沒變」。

**否決：視窗不關，顯示已受理。** 與上面差別不大，多一步手動關閉，而那一步什麼都沒告訴你。

手動重查還有一個好處：**補貨會順帶喚醒缺貨佇列**，所以重查看到的可能是「在手 +50、預留也
+50」——貨當場被等待中的單吃掉。那是這個系統最值得看的一幕，讓它由使用者自己點出來，比在
背景悄悄發生好。

### 5. left join 在前端做

**否決：後端回完整名單（含零）。** 前端最簡單，代價是 `allocation` 首次依賴 `catalog`——而
它現在對 `archone.catalog` 是零 import，`stock_pools` 也沒有指向主檔的外鍵（`DevSeedData`
的註解明寫這件事）。

**否決：在 demo 那邊開一支跨 context 的 BFF 查詢。** 邊界不被破壞（demo 本來就跨），但多一層
只服務一個畫面的程式碼。

前端已經為了把代碼還原成看得懂的字載了整份主檔。它兩半都有，join 在它那裡是零成本。

### 6. 移除舊端點

`GET /stock-pool/{sku}?ownerId=` 在 production 的呼叫端只有 `frontend/src/api/client.ts`
一處。連帶 `GetStockPoolUsecase.getBatches` 與 `StockPoolRepository.findBatchesAcrossNodes`
（production 也只有那一個呼叫端）。

**否決：保留兩支並存。** 「某個 SKU 在所有倉的分布」是真的另一個問題，R3 加分倉庫存就是為了
讓它有資料。但沒有畫面問它，而一支沒人呼叫的端點與它的 spec 要繼續維護——更麻煩的是兩支只
差在查詢軸的庫存查詢會讓人每次都要想一下該用哪一支。

**否決：保留端點且畫面加一個「按 SKU 跨倉看」的切換。** 那讓庫存頁有兩種模式，範圍遠大於
這個 change。

真的需要跨倉檢視時再開一個 change，那時它會有一個明確的畫面需求，而不是「以前有所以留著」。

### 7. 空倉回 200 + 空清單，不驗指派關係

舊端點查無回 404。換軸之後那個語意不成立：**空倉是正常答案**，而且決策 2 讓空倉仍然有完整
畫面（全部規格、全部 0、每列都能補貨）——那正是新倉上線時要用的畫面，回 404 會讓它空掉。

**否決：空倉 200，但貨主–倉未指派回 404。** API 誠實度最高，分得出「空的倉」與「不屬於你的
倉」。代價是要讀 `catalog` 的 `FulfillmentNodeRepository`——與決策 5 相反。前端的倉別下拉本來
就只列已指派的倉，所以這個區別在畫面上到不了。

### 8. 在手含過期，可承諾不含，另加一欄已過期

配貨的取批查詢是 `expiryDate >= :today`，所以過期的批**永遠配不到**。

以種子的甲貨主北部倉烏龍茶（四批，其中 25 件已過期）為例：

| 欄 | 值 | 它是什麼 |
| --- | --- | --- |
| 在手 | 155 | 倉庫裡真的有這麼多——物理事實 |
| 已預留 | 80 | |
| 可承諾 | 50 | 配貨真的兌現得了的量 |
| 已過期 | 25 | 上面三個對不起來的差額 |

**否決：三個數字都含過期（可承諾 75）。** 三者對得起來，但可承諾是假的——配貨只給得出 50。
畫面上看得到貨卻配不到的那一刻會看起來像配貨壞了。

**否決：三個數字都只算未過期（在手 130）。** 三者也對得起來，但那 25 件在列表層完全消失，
要展開才看得到——而使用者不會去展開一個看起來沒問題的列。

在手與可承諾各自誠實、差額由第四欄解釋。那個差額正是「要報廢還是要進貨」的分歧點。

### 9. 入庫日與效期預帶該規格最近效期那一批

預設值是在替使用者選意圖：預帶既有批的日期 = 加到那一批；改掉日期 = 開新批。

**否決：兩欄留空（現狀）。** 每次補貨都是明確決定，但那兩個值要先展開該列才抄得出來。

**否決：預帶今天與今天 + 一年。** 打字最少，但入庫日取今天代表**每天都會開一列新的**，庫存
散成一堆小批。`run.sh` 的註解明寫這正是壓測 fixture 刻意固定日期要避開的事——庫存一散開，
熱點競爭的強度就完全不同，而 checks 仍然會全過。

零庫存的規格沒有東西可預帶，兩欄留空。

### 10. 列表依主檔順序（款 → 規格）固定排列

決策 4 讓補完貨要手動重查才看得到結果，所以**排序穩不穩定直接決定你看不看得出差別**。

**否決：可承諾少的在前。** 把要補的推到眼前，零庫存的自然排最上面。代價是你補完那一列重查
後它就跳到列表尾巴——而重查的整個目的就是看那一列變了什麼。

**否決：有庫存的在前、零庫存的沉底。** 同樣的問題：補完第一次貨那一列會從底下跳到上半部。

固定排序還有第二個好處：別人下單吃掉庫存也不會讓列跳位。

## Risks / Trade-offs

**一個貨主有幾千個規格時，列表會很長。** 決策 2 的代價。這是操作台不是產品介面
（`frontend/README.md` 開宗明義），種子只有幾個規格。真的變成問題時的方向是搜尋框，不是
回頭砍掉零庫存那幾列——那會把「這個倉缺什麼」一起砍掉。

**展開狀態不跨重查保留。** 重查會重建列表，展開的列會收回去。可以記住，但那要決定「規格被
補到別的倉導致它消失時怎麼辦」之類的邊界，而收回去沒有任何歧義。先收回去。

**移除舊端點是 BREAKING。** 這個系統沒有第三方呼叫端，前端與後端一起部署，所以實際風險是零。
記在這裡是因為它在 spec 上確實是移除一條 requirement。
