## Context

這個 change 的觸發點是 R4 的一個附帶發現：FIFO 佇列要依時間排序，追查排序鍵時發現
`orders.placed_at` 的值是 `Instant.now()`，也就是收單時刻，而不是名字說的下單時刻。

追下去發現不只是名字問題——上游的下單時間根本沒有被收集。

## Goals / Non-Goals

**Goals**

- 一個欄位存一件事，名字說出它存的是什麼
- 讓上游能傳下單時間，並存下來
- 排序行為完全不變

**Non-Goals**

- 不改任何排序基準或佇列語意
- 不為新欄位建立消費端（SLA 計算、報表都不在這裡）
- 不碰 R4 的任何範圍

## Decisions

### 收單時刻叫 `received_at`

它是「我們收到並接受這張單的時刻」。`order-intake` 這個 capability 的名字就是收單，用同一個
語彙。

不用 `created_at`：那描述的是資料列被建立，是技術事實。訂單不是被我們建立的，是被我們收到的
——差別在於當系統日後支援補單、匯入歷史資料時，「建立」會指向錯的東西。

不用 `accepted_at`：被拒絕的命令根本不會有列，「accepted」是多餘的限定。

### 上游的下單時間可空

上游不一定給。強制 NOT NULL 就得在沒給時編一個值，而唯一能編的值是收單時刻——那等於把兩個
欄位又合回一個，只是換了種方式。

**可空的代價要記住：它因此不能當排序鍵。** FIFO 佇列與最近訂單列表都繼續用 `received_at`。

### 只擋明顯荒謬的下單時間，不做嚴格比較

下單時間晚於收單時間在邏輯上不可能，但**上游的時鐘與我們的不同步**，快個幾秒是常態。嚴格比較
會把正常的單擋在門外。

因此規則是：晚於收單時刻**超過一個容忍窗**才拒絕。容忍窗設為 5 分鐘——足以吸收時鐘偏移與網路
延遲，而真正的資料錯誤（填成明天、填成下個月）都遠超過它。

不設下限。三個月前的下單時間可能是歷史資料匯入，那是合法的。

### 事件仍帶收單時刻

R3 把生命週期事件瘦成只帶識別碼與時間戳。那個時間戳描述的是「這件事在我們系統裡何時發生」，
所以仍取 `received_at`。上游的下單時間是訂單的屬性，不是事件的屬性——需要它的消費端重讀訂單
就拿得到，這正是那次瘦身的理由。

### 前端兩個都顯示

訂單頁已經在攤開四個階段時間戳。少顯示一個會讓人以為系統沒存，而它們的差值正是這個 change
存在的理由——上游延遲了多久，一眼就看得出來。

上游沒給時顯示為空，不填入收單時刻：填了就與「上游真的給了同一個時間」在畫面上長得一樣。

## Implementation Contract

| 元件 | 動作 |

| `Order` | `placedAt` → `receivedAt`；新增 `placedAt`（可空）與容忍窗驗證 |
| `PlaceOrderCommand`、`PlaceOrderUsecase` | 接受可選的下單時間 |
| `OrderEntity`、`OrderMapper`、`OrderRepositoryImpl` | 兩個欄位 |
| `PlaceOrderRequest` | 新增可選欄位 |
| `OrderStatusResponse` | `placedAt` → `receivedAt`；新增 `placedAt` |
| 前端 `types.ts`、`OrderTable` | 兩個欄位與標題 |
| `DevSeedDataInitializer` | 種子含一張有上游時間、一張沒有的單 |

## Risks / Trade-offs

**同一個名字換了意義。** 舊的 `placedAt` 是收單時刻、新的 `placedAt` 是下單時刻。若有讀取端只
跟著改名而沒改語意，它會安靜地讀到不同的東西。這個 repo 的唯一消費端是自己的前端，在同一次
改完；但這是這次改動裡唯一無法靠型別擋住的風險。

**容忍窗是個猜測。** 5 分鐘沒有量測支持，它的用途是擋住「填成明天」這種等級的錯誤，不是精確
的時鐘校正。寫成可設定值，並在註解裡說明它擋的是什麼。
