# frontend

`order-promising` 的操作台：三頁、本機執行、給螢幕分享時邊操作邊解說用。它不是產品
介面，也不打算變成產品介面。

## 啟動

收貨使用正式的同步 `POST /stock-receipts`，不受 profile 限制。只有 `/demo/config` 需要後端
以 dev profile 註冊；其他 profile 下仍可收貨，但不顯示 demo 分區策略。

最省事的方式是用 `e2e/perf` 那套（PostgreSQL + Kafka + Debezium 都會一起起來）：

```bash
./e2e/perf/run.sh up      # 基礎設施 + app（dev profile）+ Debezium connector
cd frontend && npm install && npm run dev
```

開 http://localhost:28295 。埠被佔用時 Vite 會直接失敗而不是換一個（`strictPort`）——換埠會讓「我開的到底是哪一份」變成要翻 log 才知道。

**不要用 `docker compose up` 代替 `run.sh up`。** app 不在 compose 裡，而 Debezium
connector 必須等 app 跑完 Flyway 建出 `event_outbox` 才能註冊——少了那步，下單會成功、
`OrderPlaced` 卻出不了 outbox，訂單就永遠停在 `PENDING`，畫面上看不出任何錯誤。

後端位址只寫在 `vite.config.ts` 的 dev proxy 裡，不出現在任何原始碼中。要指到別的地方
設環境變數即可，不用改元件：

```bash
ARCHONE_BACKEND_ORIGIN=http://localhost:9090 npm run dev
```

## 三頁在做什麼

**訂單頁**（預設）——下單表單 ＋ 最近 20 筆訂單。列表一列攤開訂單的全部欄位，包含四個
階段時間戳；沒有「點開看詳細」，因為那會是同一份資料的第二次呈現。

**庫存頁**——查**某貨主在某倉**放了什麼，並從貨品那一列收貨。兩者是一個連續動作：看到可承諾
量是 0、補一批、再查一次。

**主檔瀏覽頁**——唯讀查看貨主、可出貨倉與庫位、商品及 SKU。它重用下單與庫存頁已使用的
Catalog API，不提供新增、修改或刪除；UUID 與代碼保留下來，方便 DEMO 時核對跨 Context correlation。

查詢軸刻意是 `(貨主, 倉別)` 而不是 SKU。**配貨從不跨倉**——每一次都鎖在一個倉裡，所以「一個
SKU 散在哪些倉」是一個沒有任何一次配貨會照著做的問題；而倉庫每天真正要問的是「這裡放了什麼、
還缺什麼」。

**一列一個規格，批是展開後的第二層。** 四批同一個規格會佔四列，而「這個規格總共還能出幾件」
才是決定要不要收貨的數字。展開之後才是那幾批，順序就是配貨會取用的順序（FEFO：效期近的先出，
同效期則先進先出）——所以第一批就是下一張單會吃到的那一批。

**一列有四個數字，而且它們刻意對不起來：**

| 欄 | 算法 |
| --- | --- |
| 在手 | 全部批的加總，**含過期** |
| 已預留 | 全部批的加總 |
| 可承諾 | **只算未過期**的批 |
| 已過期 | 過期批的在手加總 |

在手是倉庫裡真的有多少（物理事實），可承諾是配貨真的兌現得了的量（取批查詢是「效期 >= 今天」）。
兩者對不起來的差額就是第四欄，而**那個差額正是「要報廢還是要進貨」的分歧點**。三個數字硬湊成
對得起來的版本會讓可承諾說謊，而「有貨卻配不到」那一刻會看起來像配貨壞了。

過期的批在展開後也列出來並標記，不是濾掉。沒過期但被預留光的批標成「已預留完」而不是與過期
共用一個「不可配」——配貨眼中兩者相同，但操作上一個要報廢、一個只是等出貨。

**列出該貨主的每一個規格，這個倉沒有的顯示 0。** 那些零就是這個倉缺什麼，收貨鍵因此到得了每
一個規格；只列有貨的會讓這個倉從未放過的貨品再也進不去。倉裡有貨但主檔查不到的（壓測用的
`HOT-SKU` 就是）也照樣列出來，只是沒有品名——漏掉它等於畫面上少報倉庫裡真實存在的貨。

**列的順序照主檔的款 → 規格，不隨數量變動。** 收貨的結果要手動重查才看得到，排序一旦跟著數量
走，你補的那一列就會跳走——而重查的整個目的就是看它變了什麼。

**收貨從那一列的視窗進去。** 貨主、倉別、貨品唯讀顯示——三者已經由查詢與被點的那一列決定，可改
就會出現「點的是北部倉、寫進去的是中部倉」這種矛盾。只有入庫日、效期、數量要填，而前兩者預帶
該規格最近效期、**且還沒過期**的那一批：不改直接送就是往現有的批加貨，改掉日期才是開一批新的。
（跳過過期的批是刻意的——往它加貨等於製造配貨永遠取不到的死庫存。）

**送出後視窗會關，但數字不會自動覆寫。** 收貨回 `200` 時 inbound execution 與 StockPool 已
在同一交易完成，畫面顯示實收數量，並保留一顆重新查詢。收貨可能同時把新量
配置給缺貨訂單，所以重查後可承諾量不一定增加。

手動重查還換來一件事：**收貨會順帶喚醒缺貨佇列**，所以重查看到的可能是「在手 +50、預留也 +50」
——貨當場被等待中的單吃掉。那是這個系統最值得看的一幕，讓它由你自己點出來，比在背景悄悄發生好。

頁首顯示後端目前生效的分區策略（`stock` 是 single-writer，其餘是 v1 的 orderId）。只顯示
不切換——那個值在後端啟動時就固定了。

## 主檔載入的代價

三頁都在進場時載入整份主檔（`useCatalog`），因為訂單列表要把 `ownerId` 與 SKU 代碼還原成
看得懂的字，而訂單契約刻意只帶 `ownerId`——名稱從畫面本來就要載的那份主檔解析即可，那是
「整個畫面查一次」，不是每一列各查一次。

代價是請求數為 `1 + N貨主 + Σ款` 的 fan-out：目前的 demo 資料（2 貨主、3 款）是 6 支。這個
數字隨主檔線性成長，而它是下單表單能用的前提。

要收掉得由後端提供一支扁平的主檔查詢（一次回攤平的 owner／product／sku），把 6 支收成 1 支。
**現在不做**：這是效能問題不是正確性問題，而且現有三支端點的資源劃分（款與規格巢狀在貨主
之下，因為編碼跨貨主撞號、貨主是它們存在的前提）是對的——扁平端點會是額外的讀取視圖，不是
取代它們。等主檔規模真的讓這個 fan-out 會痛時再做，屆時要一併決定兩者如何並存。

## 為什麼沒有自動更新

所有請求都對應一個明確的使用者動作：進頁面、送出表單、按查詢、按重新整理。沒有輪詢、
沒有計時器、沒有背景刷新——訂單頁載入完成後靜置，網路面板不會再出現任何請求。

代價是收貨之後要自己按「重新整理」才看得到訂單狀態變化。這在「操作者本人邊操作邊解說」
的情境下不是負擔，反而讓「配置是非同步的」這件事在操作上顯而易見。

## 一個典型的 demo 流程

用 `SKU-EMPTY`（ATP 是 0）：

1. 庫存頁選乙貨主 + 南部倉 → `SKU-EMPTY` 那一列四個數字都是 0，展開看得到一批在手 0 的批
2. 訂單頁對它下幾張單 → 看到 `PENDING`；缺貨時仍維持 `PENDING`，等待佇列由庫存作業呈現
3. 回庫存頁，點 `SKU-EMPTY` 那一列的收貨 → 日期已經預帶好，直接送 → 顯示「已完成收貨」
4. 訂單頁按重新整理 → 看到那批訂單依 FIFO 轉成 `ALLOCATED`、`allocatedAt` 有值
5. 回庫存頁按「重新查詢」 → 那一列的已預留量上去了。**把視窗裡的日期改掉再補一次，展開會
   多出一列**——那正是「五個維度全等才是同一批」

另外兩條值得走的：

**甲貨主 + 北部倉**——`SKU-AVAILABLE` 是 在手 155 / 已預留 80 / 可承諾 50 / 已過期 25。四個
數字對不起來就是重點：多出來的 25 件出不了貨。展開看得到四批，其中兩批同效期不同入庫日、一批
已過期，一次看完 FEFO 的排序、同效期的先後、以及「有貨但已過期」三件事。

**甲貨主 + 中部倉**——空倉。畫面上仍然列出甲貨主的每一個規格、四欄都是 0、每一列都能收貨。
那正是一個新倉剛上線時的樣子，也正是最需要打開它的時候。

**乙貨主 + 南部倉的跨 SKU 單**——種子放了一張同時要 `SKU-AVAILABLE` 與 `SKU-EMPTY` 的單。
`SKU-AVAILABLE` 有 50 件、它只要 5 件，但整張單卡在 `SKU-EMPTY`，所以那 50 件一件都沒被鎖住。
**有貨卻不配**，而那正是 ship-complete 的內容：整張配或整張不配。補齊 `SKU-EMPTY` 之後重查，
`SKU-AVAILABLE` 的已預留才會跟著跳上去。

種子已經在乙貨主的佇列裡放了一張 `SKU-EMPTY` 的缺貨單，`backordered_since` 比你當場下的
都早——補乙貨主的貨時它會**排在最前面**被配到。那不是 bug，是 FIFO 本來的樣子。

收貨要選貨主，而佇列是按貨主分開的：補甲貨主不會動到乙貨主的單，即使兩邊的 SKU 代碼相同。
