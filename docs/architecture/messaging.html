01

一條事件，兩個本地交易

Messaging 負責可靠傳遞與消費基礎設施；業務語意由各 bounded context 擁有。

PRODUCER業務服務

Application Event 經 port／adapter 轉成 Integration Event。

→
LOCAL TX APostgreSQL Outbox

業務資料與 event_outbox 原子提交。

→
CDC / BROKERDebezium → Kafka

讀取 WAL，依 route 與 partition key 發布。

→
LOCAL TX BConsumer + Inbox

去重、業務變更及後續 Outbox 原子提交。

本地交易保證原子性，Inbox 處理重複投遞。

DB commit 與 Kafka offset commit 並非同一個分散式 transaction。處理成功後若 offset 尚未提交便重啟，訊息可能再次抵達；穩定的 subscriber ID 與 message ID 讓 Inbox 能判定重複。這不代表跨系統的 exactly-once。

業務邊界

Application／Domain 不直接依賴 versioned Integration Event、IntegrationEventPublication 或 IntegrationEventPublisher。正常業務 publication 一律經 Outbox。

傳輸邊界

正常事件由 Debezium 發到 Kafka；DLT recovery 與受控 replay 是使用 Kafka producer 的特殊基礎設施路徑。

03

Producer：從業務事實到 Outbox

業務交易與發送意圖一起落盤，Kafka 發送由 CDC 接手。

CALLER TRANSACTION · 同一個業務交易內同步執行
BUSINESSUsecase → Application Event

產生已發生事實；交給 application.port.*Publisher。

→
BOUNDARY*IntegrationEventAdapter

轉成 versioned contract 與 publication；必要時使用純 Translator。

→
FRAMEWORKIntegrationEventPublisher

mapper／serde 轉成 Message，交給 MessageProducer。

→
PERSISTENCEJDBC Outbox INSERT

要求 caller transaction；與業務資料一起 commit／rollback。

AFTER COMMITPostgreSQL WAL

已提交 Outbox 變更可由 CDC 讀取。

→
CONNECTDebezium EventRouter

route → topic；partition_key → record key；傳遞 payload／headers。

→
DELIVERYKafka topic

交由各 consumer group 消費。

Producer 的成功，表示 Outbox 已寫入當前交易。

只有 caller transaction 提交後才持久化；不代表 Kafka 或下游已完成。Outbox 寫入失敗應讓整個業務交易 rollback；需要重試時重試完整業務操作，而不是單獨再 publish 一次。

同一 Application Event 可由 Adapter 在原交易內同步產生多個面向不同 audience 的 publication。複雜 Translator 只做轉換，不查 DB、不改 Domain，也不直接發布。

05

重試與 DLT：失敗如何流動

切換情境，對照目前的 application policy 與 framework recovery 行為。

樂觀鎖衝突

本地先嘗試 3 次（首次 + 額外 2 次），每次重新執行交易；耗盡後交給 Kafka 層。

首次 delivery：最多 3 次交易1s → 再投遞2s → 再投遞4s → 再投遞8s → 再投遞耗盡 → DLT

持續同類失敗的一輪重試，最多 3 × 5 = 15 次交易嘗試。

這是 monolith 目前的 policy，不是框架強制的通用預設。

本地重試間隔 100ms；Kafka 退避為 1、2、4、8 秒，另加處理與 timeout 的時間。次數不是跨重啟／rebalance 的永久上限。DB 長時間中斷仍可能耗盡後進 DLT；DB 恢復不會自動 replay。

框架中的 DLT 發送接點

DeadLetterPublishingRecoverer recoverer =
    new DeadLetterPublishingRecoverer(kafkaOperations);
recoverer.setFailIfSendResultIsError(true);

DefaultErrorHandler errorHandler = new DefaultErrorHandler(
    recoverer, retryBackOff, observationHooks.observingBackOffHandler());

errorHandler.setBackOffFunction((record, failure) ->
    failureClassifier.classify(failure).retryable()
        ? retryBackOff : NO_RETRY);

可重試錯誤在耗盡後由 recoverer 發送；不可重試錯誤不經重試就進 recovery。未知 handler 例外目前預設不可重試。

06

為什麼有兩個 factory？

介面描述 runtime 需要什麼；建構工具提供 retry／DLT 的具體組合。

SPRING BEAN METHODkafkaSubscriptionErrorHandlerFactory()

AutoConfiguration 的組裝方法；回傳下面的介面實例。

→
INTERFACEKafkaSubscriptionErrorHandlerFactory

定義 create(subscription) → Optional<CommonErrorHandler>。

→
BUILDERKafkaDeadLetterErrorHandlerFactory

perSubscription() 回傳 lambda 實作；再建立重試／DLT handler。

建立一次 factory，每個 subscription 建立自己的 handler

// Bean 組裝
return KafkaDeadLetterErrorHandlerFactory.perSubscription(
    kafkaOperations, failurePolicyResolver, observerFactory);

// 訂閱建立時
policy.commonErrorHandler()
    .or(() -> errorHandlerFactory.create(subscription))
    .ifPresent(container::setCommonErrorHandler);
為什麼依 subscription 建立？

同一 topic 可有多個 subscriber／group。個別建立能帶入正確的 subscriber ID、group、logical channel、failure policy 與觀測 metadata。

沒有執行兩套 error handler

優先使用 policy.commonErrorHandler；未提供才由 factory 建立。介面與建構工具也不是兩輪 retry。

預設 DLT factory Bean 需有 KafkaConsumerFailurePolicyResolver 與 KafkaOperations，且沒有自訂同型 Bean。這是條件式組裝；不能只引入任意 consumer library 就假設 DLT 已啟用。

07

恢復操作與目前缺口

自動送入 DLT 已完成；人工恢復還需要受控的執行入口。

IMPLEMENTEDDLT record

包含原始 record metadata 與實際 subscription 身分。

→
IMPLEMENTEDReplayRecordFactory

驗證 metadata、重建 ProducerRecord、移除 DLT-only headers；不發送。

→
NOT IMPLEMENTEDReplay CLI／API

選取、預覽、權限與操作紀錄、受控送回原 topic。

→
EXISTING PATH原 topic → Consumers

保留 message ID；成功過的 subscriber 可由 Inbox 去重。

Replay 不等於重設 offset，也不是業務補償。

重播建立新的 Kafka record，無法還原原 offset 或回插原始時序。送回原 topic 會被其相關訂閱者接收；即使保留 partition／key，也需要評估晚到事件與業務狀態是否仍相容。

穩定 identity 與設定邊界
  • subscriberId：Inbox namespace；consumer group 可由 ConsumerGroupMapping 另行映射。
  • messageId：retry／replay 保留，否則會被當成新事件。
  • aggregateId：domain identity；partitionKey：ordering／contention boundary。
  • spring.kafka.listener.*：container 全域 baseline；KafkaSubscriptionPolicy 僅提供單一訂閱的覆寫。
  • IntegrationEventNameMapping：顯式允許 stable event type／version，不依 Java FQCN 動態載入。
