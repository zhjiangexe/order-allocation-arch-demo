01 · 先建立共同語言

名詞解釋

先把「來源、需求、供給、規劃結果、已承諾事實」分開。若這五種東西混用，後面的流程一定會看起來像一大坨。

Source

貨主出貨訂單

需求的業務起點，由 Ordering 擁有。Inventory 不載入 Order aggregate，而只讀取已發布的 allocation source projection。

真相：為何要出貨
Source port

OrderStockMovementSource

來源邊界介面。輸入 orderId，輸出 source-neutral 的 RegisterStockOperationCommand，隔離 Order 語彙。

責任：翻譯，不配貨
Policy group

StockOperation

共同套用 policy 的 Move 分組。保存 source、owner、起訖庫位、時程與摘要狀態；本身沒有 SKU 與數量。

真相：哪些 Move 一起處理
Demand

StockMove

一個 SKU 從某庫位到另一庫位的需求。demandQuantity 是數量真相；一張訂單行正規化成一個 canonical Move。

真相：什麼貨、多少、從哪到哪
Supply

StockQuant

owner × location × SKU × inDate × expiryDate 的物化庫存餘額。ATP = onHand − reserved，不另存第二份。

真相：哪一批還能承諾多少
Planning input

StockOperationDemand

從已確認的 Operation／Moves 複製出的不可變規劃輸入，攜帶 optimistic version，讓規劃不必操作 persistence aggregate。

用途：純演算法的需求快照
Planning input

StockAllocationSupply

本次 allocation 可考慮的不可變供給集合，固定 owner／location scope，並為每個需求 SKU 保留明確群組。

用途：純演算法的共享供給邊界
Supply row

StockQuantSupply

從 StockQuant SQL row 直接投影的不可變供給，只攜帶 Quant identity、scope、FEFO 日期與 ATP，不暴露 mutable aggregate。

血統：一筆 StockQuant 的規劃投影
Pure result

StockAllocationProposal

Planner 算出的「建議 Move 應取哪些 Quant」。尚未鎖資料列、尚未改庫存，不具權威性，可以因併發而失效。

事實：只是方案，不是承諾
Committed relation

StockMoveLine

持久化的 Move × Quant 預留關係。一個 Move 跨兩批就有兩列。這是「已配到哪批」的權威事實，但不是 WMS 實際揀貨紀錄。

真相：Inventory 已鎖住哪一批
Policy

SHIP_COMPLETE

整個 Operation 的所有 Move 必須一次完整覆蓋；只要一個 SKU 不足，Proposal 就完全不含 reservation，不做部分配貨。

規則：全有或全無
Selection rule

FEFO

First Expired, First Out。先取較早效期，再以入庫日、Quant ID 穩定排序，結果可重現。

規則：供給批次的消耗順序
Concurrency

Predecessor

同 owner、同來源庫位、共享 SKU 且更早入隊的 CONFIRMED Operation。存在時，後單不越過前單搶同一 SKU。

規則：shared-SKU strict FIFO
Messaging

Inbox／Outbox

Inbox 防止同一 subscriber 重複處理事件；Outbox 讓「庫存已配貨」與待發布事件在同一 DB transaction 一起提交。

保證：至少一次傳輸下的本地一致性
最容易混淆的一句話：Proposal 說「如果現在提交，我打算怎麼配」；StockMoveLine 與 Quant reserved counter 才說「Inventory 已經承諾了什麼」。而 WMS 最後實際揀了哪批，仍是下一個執行／過帳階段的事實，不在本 Use Case 內。
02 · Source → Process → Target

一張圖先看懂邊界

AllocateOrderUsecase 不是演算法本體，而是把三段能力串起來：來源正規化、movement intent 註冊、共用 assignment pipeline。

Use Case 做什麼

選擇正確的 collaborator 並安排順序；不自己理解 FEFO、不自己操作 JPA。

Planner 做什麼

把 immutable StockOperationDemand 與 StockAllocationSupply 配對，輸出可驗證的完整 proposal。

Transaction 做什麼

取得權威資料與鎖、重驗 proposal，才改 counters、建立 MoveLine 與發布事件。

03 · 進入點與隱形外框

誰呼叫 AllocateOrderUsecase？

有兩個 inbound adapter；兩者最後都只傳 AllocateOrderCommand(orderId)，但事件模式多一層 Inbox idempotency。

模式入口類別呼叫鏈交易特性
Events（預設） AllocationOrderPlacedEventConsumer OrderPlacedIntegrationEvent → onOrderPlaced → execute TransactionalIdempotencyMessageHandlerDecorator 開啟 transaction，先 claim event_inbox；Use Case 加入同一 transaction。
Temporal TemporalInventoryAllocationActivitiesAdapter requestAllocation → execute 沒有訊息 Inbox；由 AllocateOrderUsecase.execute 的 @Transactional 建立本地 transaction。
04 · Chronological Walkthrough

從頭到尾，逐步執行

下面每一步都標明主要 class／interface、讀寫效果，以及「在哪裡停止」。

0

收到 OrderPlaced 或 Temporal Activity

AllocationOrderPlacedEventConsumer.onOrderPlaced(event) ｜ TemporalInventoryAllocationActivitiesAdapter.requestAllocation(input)

Inbound adapter 不傳整個 Order，只建立 AllocateOrderCommand(orderId)。事件模式先由 messaging decorator 用 (subscriberId, eventId) 對 event_inbox 做 insert-if-absent。

寫入事件模式先 provisional 寫入 event_inbox；若後面 rollback，claim 也 rollback。
1

Use Case 開始編排

AllocateOrderUsecase.execute(AllocateOrderCommand) · @Transactional

這個類別只有三個 collaborator：

  • OrderStockMovementSource：把 Order source 轉成 movement command。
  • StockOperationRegistrar：把需求意圖持久化。
  • StockOperationAssignmentCoordinator：選候選、讀供給、規劃、嘗試承諾。
設計意義Use Case 只負責流程順序，沒有 FEFO SQL、沒有 reserve counter、沒有 JPA entity。
2

讀取 Order-owned source projection

OrderStockMovementSource.find(orderId) → OrderStockMovementAdapter → JpaOrderAllocationSourceRepository

Adapter 從 read-only stock_order_movement_sources 依 sourceId 讀取並以 source line 排序。它檢查所有行是否屬於同一 owner、facility、operation type、來源與目的庫位。

通過後正規化成 RegisterStockOperationCommand：方向固定 OUTBOUND、來源為 StockOperationSource.primaryOrder(...)、policy 固定 SHIP_COMPLETE，每個來源行成為一個 MovementLine。

分支查無 rows → Optional.empty() → Use Case 正常 return；不建立任何 movement。這代表 cancelled 或不存在的 source。
3

冪等註冊 movement intent

StockOperationRegistrar.register(command) → StockOperationStore.findBySource(source)

先用 (sourceType, sourceId, allocationUnitKey) 尋找既有 Operation：

  • 不存在：建立一個 StockOperation(CONFIRMED)，再依已排序 source line 建立多個 StockMove(CONFIRMED)。
  • 已存在且內容相同：回放既有 Operation／Moves，created=false。
  • 已存在但不可變內容不同：拋 SourceMovementConflictException，整個 transaction rollback。
寫入stock_operations、stock_moves。此刻只是 confirmed demand，尚無 stock_move_lines，Quant 也沒變。
4

讀取 assignment candidate 與前置單

StockOperationAssignmentCoordinator.tryAssign(id) → StockOperationAssignmentCandidateStore.findByOperationId → JdbcStockOperationAssignmentCandidateStore

JDBC projection 直接 join stock_operations 與 stock_moves，只接受 CONFIRMED、非 INBOUND、具有 source 的完整 operation demand，組成 StockOperationDemand。

接著查同 owner、同來源庫位、共享至少一個 SKU、且 (enqueuedAt, id) 更早的 CONFIRMED operation。

分支找到 StockOperationPredecessor → 立即回傳 Optional.empty()，連供給都不查；後單不能越過前單搶共享 SKU。
5

讀取 Planner 專用的 FEFO supply projection

StockAllocationSupplyStore.findBySku(...) → JdbcStockAllocationSupplyStore

用 owner、fromLocation、所有 SKU、business today 查 stock_pools。SQL 排除已過期與 ATP=0 的列，並按 skuCode → expiryDate → inDate → id 排序。

SQL row 直接轉成 immutable StockQuantSupply，再包成 StockAllocationSupply；不建立 mutable StockQuant，也沒有加 row lock。

只讀此時看到的是 optimistic supply snapshot；另一個 transaction 仍可能先預留同一批貨。
6

純演算法產生 Proposal

MovementAssignmentPlanner.plan(demand, supply)

先彙總各 SKU 的需求與 ATP。若任一 SKU 不足，建立 StockAllocationProposal.insufficient，只帶完整缺口 SkuQuantities，proposed move line list 必須為空。

若全部足夠，依 Move lineSequence 逐一從每個 SKU 的 FEFO queue 取量，產生多個 ProposedMoveLine(moveId, quantId, qty)。Proposal constructor 再檢查每個 Move 是否被精確覆蓋。

純計算沒有 Repository、沒有 lock、沒有 domain aggregate mutation。ready 也不等於成功，只代表值得進交易重驗。
7

進入唯一的 assignment commit boundary

StockAllocationCommitter.commit(proposal, today, occurredAt) · @Transactional

只接受 ready proposal，並用固定順序取得權威資料：

  1. StockOperationStore.findLockedById：PESSIMISTIC_WRITE 鎖 Operation。
  2. StockMoveStore.findLockedByStockOperationIdInIdOrder：按 Move ID 鎖整組 Moves。
  3. 載入既有 MoveLines，組成暫態驗證模型 StockOperationComposite；DB lock 由外層 transaction 與 ForUpdate 查詢持有，Composite 本身不取得或擁有 lock。
  4. 重查 predecessor，防止規劃與提交之間隊列條件改變。
  5. StockQuantStore.findByIdsForUpdate：按全域順序鎖 Proposal 涉及的 Quants。
併發策略Planner 可以樂觀且快速；只有短暫 commit phase 鎖真正要改的列，並以一致順序降低 deadlock。
8

在鎖內重驗 Proposal 是否仍成立

StockOperationComposite + MoveQuantAllocationSet.validateAndOrder(...)

逐項確認：Operation／Move 仍為 CONFIRMED、version 未變、沒有殘留 MoveLine、Proposal 精確覆蓋整組 Moves、Quant 都存在、owner/location/SKU scope 正確、未過期、目前 ATP 仍足夠。

失效處理供給或版本已變 → StaleStockAllocationProposalException → AOP 轉為 OptimisticLockingFailureException → messaging retry；本次 Inbox／註冊／配貨全部 rollback。
9

把 Proposal 轉成權威配貨事實

StockQuant.reserve → StockMoveLine → StockMove.assign → StockOperation.assign

驗證通過後才真正 mutation：

  • 每個 Quant 的 reservedQuantity += proposal quantity，on-hand 不變。
  • 每個 move-to-quant allocation 建立一列永久的 StockMoveLine。
  • 全部 Move 變成 ASSIGNED 並記錄同一 assignedAt。
  • Operation 的摘要狀態變成 ASSIGNED。
寫入stock_pools、stock_move_lines、stock_moves、stock_operations。
10

建立結果並寫入 Outbox

StockOperationAssignmentResultFactory → OrderStockOperationAssignedPublicationFactory → IntegrationEventPublisher

StockOperationAssignmentResult 包含 Operation、每個 assigned Move 及其 batch picks。若 sourceType=ORDER，factory 轉成 OrderAllocationCommittedIntegrationEvent。

IntegrationEventPublisher.publish 最終在 caller-owned transaction 中 insert event_outbox。成功回傳只代表 Outbox row 已被接受，不代表 Kafka 已立即收到；後續由 CDC 發送。

原子提交DB commit 後，Inbox、movement intent、reservation facts、ASSIGNED states、Outbox 同時可見；任何一步失敗則全部不可見。

把主幹壓成可讀的 pseudo-code

// transaction：事件模式還包含先前的 Inbox claim source = orderSource.find(orderId) if (source.isEmpty()) return registered = registrar.register(source.command()) candidate = stockOperationAssignmentCandidateStore.findByOperationId(registered.operationId()) if (candidate.hasPredecessor()) return supply = stockAllocationSupplyStore.findBySku(candidate.demand().scopeAndSkus()) proposal = planner.plan(candidate.demand(), supply) // pure if (proposal.isInsufficient()) return result = allocationCommitter.commit(proposal) // lock → revalidate → apply outbox.publish(OrderAllocationCommitted(result)) // commit

1. Use Case：只編排 source → register → assign

AllocateOrderUsecase.execute() 
@Transactional
public void execute(AllocateOrderCommand command) {
    // 【只讀】請 Order source port 把來源資料正規化成 Inventory command。
    Optional<RegisterStockOperationCommand> source =
            orderSource.find(command.orderId());

    if (source.isEmpty()) {
        // 【分支】來源 projection 沒有資料：視為不存在或已取消，正常結束。
        // 不建立 Operation／Move，也不嘗試配貨。
        return;
    }

    // 【寫入 intent】建立或重播 CONFIRMED Operation 與 Moves。
    var registered = movementRegistrar.register(source.get());

    // 【嘗試承諾】只嘗試剛註冊的這一組 movement，不掃描整個 backlog。
    assignmentCoordinator.tryAssign(registered.operation().id());
}

這裡刻意沒有 FEFO、SQL 與 reserve counter；它們分別屬於 Planner、focused Supply Store adapter 與 Allocation Committer。

2. Source Adapter：Order 語彙在這裡終止

OrderStockMovementAdapter.find() 
public Optional<RegisterStockOperationCommand> find(UUID orderId) {
    // 【只讀 source adapter】依 orderId 讀 Order-owned allocation source projection。
    List<OrderAllocationSourceLineEntity> rows =
            repository.findBySourceIdOrderBySourceLineIdAsc(orderId);

    if (rows.isEmpty()) {
        // 【分支】沒有可供 Inventory 建立 movement 的來源事實。
        return Optional.empty();
    }

    var first = rows.getFirst();
    // 確保同一個 source unit 沒有跨 owner、facility 或起訖庫位。
    requireOneResolvedScope(orderId, first, rows);

    // 【純轉譯】從這裡開始不再使用 OrderLine 等 Ordering domain 語彙。
    return Optional.of(new RegisterStockOperationCommand(
            first.getStockOperationTypeId(),
            StockOperationDirection.OUTBOUND,
            StockOperationSource.primaryOrder(orderId.toString()),
            first.getOwnerId(),
            first.getSourceLocationId(),
            first.getDestinationLocationId(),
            MovementAssignmentPolicy.SHIP_COMPLETE,
            first.getEnqueuedAt(),
            first.getRequiredBy(),
            first.getReleasePriority(),
            rows.stream()
                    // 每個來源行正規化為一個 SKU movement line。
                    .map(row -> new MovementLine(
                            row.getSourceLineReferenceId().toString(),
                            row.getSkuCode(),
                            row.getQuantity()))
                    .toList()));
}

JpaOrderAllocationSourceRepository 只是一個 source projection reader；它不會載入或修改 Order aggregate。

3. Registrar：建立可等待的 durable demand

StockOperationRegistrar.register() 
@Transactional
public StockOperationRegistrationResult register(RegisterStockOperationCommand command) {
    // 【只讀】先以 source identity 找既有 Operation，避免同一來源建立兩份需求。
    return stockOperationStore.findBySource(command.source())
            // 已存在：比較所有不可變 registration content。
            .map(existing -> replay(command, existing))
            // 不存在：建立新的 canonical movement intent。
            .orElseGet(() -> create(command));
}

private StockOperationRegistrationResult create(RegisterStockOperationCommand command) {
    UUID operationId = idSupplier.get();

    // 【建立 Domain Object】Operation 只負責分組與 policy，沒有 SKU 數量。
    StockOperation operation = StockOperation.confirmedStockConsumption(
            operationId, ..., command.assignmentPolicy(), ...);

    // 【建立 Domain Objects】每個 source line 形成一個 CONFIRMED StockMove。
    List<StockMove> moves = canonicalMoves(command, operationId);

    // 【寫入】先存分組，再按固定 ID 順序保存並 flush 全部 Moves。
    stockOperationStore.save(operation);
    List<StockMove> persistedMoves = stockMoveStore.saveAll(moves);

    // 注意：此刻尚未建立 StockMoveLine，也完全沒有修改 StockQuant。
    return new StockOperationRegistrationResult(operation, persistedMoves, true);
}

若 replay 的來源內容不同，拋出 SourceMovementConflictException；不會默默覆蓋既有 movement intent。

4. Assigner：選候選、讀供給、呼叫純 Planner

StockOperationAssignmentCoordinator.tryAssign() / attempt() 
public Optional<StockOperationAssignmentResult> tryAssign(UUID operationId) {
    // 【只讀 Query】載入一組 CONFIRMED Moves 與 strict-FIFO predecessor。
    return attempt(stockOperationAssignmentCandidateStore.findByOperationId(operationId));
}

private Optional<StockOperationAssignmentResult> attempt(AssignmentCandidate candidate) {
    if (candidate.predecessor().isPresent()) {
        // 【正常等待】有更早且共享 SKU 的 Operation，不允許越隊搶貨。
        return Optional.empty();
    }

    StockOperationDemand demand = candidate.demand();
    LocalDate today = businessClock.today();

    // 【只讀 Query】取得 owner + source location 範圍內的多 SKU FEFO supply。
    StockAllocationSupply supply = stockAllocationSupplyStore.findBySku(
            demand.ownerId(), demand.fromLocationId(), demand.skuCodes(), today);

    // 【純計算】Planner 不鎖資料列、不呼叫 data-access port、不修改 Quant。
    StockAllocationProposal proposal = planner.plan(demand, supply);

    if (!proposal.isReady()) {
        // 【正常等待】SHIP_COMPLETE 只要一個 SKU 不足，就完全不預留。
        return Optional.empty();
    }

    // 【跨越承諾邊界】只有 ready proposal 才進入鎖定與重驗 transaction。
    return Optional.of(allocationCommitter.commit(
            proposal, today, businessClock.instant()));
}

tryAssignNext(queueKey) 是日後補貨喚醒使用的同一條 pipeline，只是 candidate selection 改為從 backlog 找下一組。

5. Planner：SHIP_COMPLETE 檢查與 FEFO 配對

MovementAssignmentPlanner.plan() 
public StockAllocationProposal plan(
        StockOperationDemand demand,
        StockAllocationSupply supply) {

    // 確保 supply projection 的 owner、location 與 SKU 集合完整對應需求。
    supply.requireCovers(
            demand.ownerId(), demand.fromLocationId(), demand.skuCodes());

    // 【純計算】彙總每個 SKU 的 ATP，再計算完整缺口。
    SkuQuantities available = availableQuantities(demand, supply);
    SkuQuantities missing = demand.requiredQuantities().missingFrom(available);

    if (!missing.isEmpty()) {
        // 【SHIP_COMPLETE】不足 Proposal 只有缺口，proposed move line list 必須為空。
        return StockAllocationProposal.insufficient(demand, missing);
    }

    // 【FEFO】按 Move sequence；每個 SKU 依 expiryDate、inDate、id 取 Quant。
    List<ProposedMoveLine> proposedMoveLines =
            proposeInCanonicalFefoOrder(demand.moves(), supply);

    // ready() 還會驗證 proposedMoveLines 是否精確覆蓋每個 Move 的 demandQuantity。
    // 這仍然只是 Proposal；直到 StockAllocationCommitter 成功前都不具權威性。
    return StockAllocationProposal.ready(demand, proposedMoveLines);
}

Planner 的輸出可以在測試裡完全由輸入推導，因此 FEFO 與 SHIP_COMPLETE 不受 persistence／transaction 細節污染。

6. Allocation Committer：鎖定、重驗、原子承諾

StockAllocationCommitter.commit() 
@Transactional
public StockOperationAssignmentResult commit(
        StockAllocationProposal proposal,
        LocalDate today,
        Instant occurredAt) {

    // 1.【輸入】只接受完整 ready proposal 與明確的業務日期／時間。
    validateCommitRequest(proposal, today, occurredAt);

    // 2.【鎖定】依固定順序載入 Operation、Moves 與既有 MoveLines。
    StockOperationComposite operationComposite =
            loadOperationCompositeForUpdate(proposal.stockOperationId());

    if (operationComposite.operation().state() == StockOperationState.ASSIGNED) {
        // 3.【冪等重送】從權威 MoveLines 重建結果，不重複 reserve 或 publish。
        return reconstructCommittedResult(operationComposite);
    }

    // 4.【重驗需求】確認版本、狀態、policy、coverage 與最終 predecessor。
    validateProposalAgainstComposite(operationComposite, proposal);
    requireNoPredecessor(operationComposite.operation().id());

    // 5.【準備 mapping】中性的 move → quant → quantity 暫態資料，不是第二套 ledger。
    MoveQuantAllocationSet allocationSet =
            MoveQuantAllocationSet.fromProposal(proposal);

    // 6.【鎖定供給】依全域順序鎖 Quant，再驗 scope、expiry 與目前 ATP。
    List<StockQuant> lockedStockQuants =
            lockAndValidateStockQuants(allocationSet, operationComposite, today);

    // 7.【權威寫入】reserve Quant、建立 MoveLines、Moves／Operation 轉 ASSIGNED。
    List<StockMoveLine> committedMoveLines = applyAllocation(
            operationComposite, allocationSet, lockedStockQuants, occurredAt);

    // 8.【結果】sorting、grouping 與 facility enrichment 交給專責 factory。
    StockOperationAssignmentResult result = resultFactory.create(
            operationComposite.operation(),
            operationComposite.moves(),
            committedMoveLines,
            occurredAt);

    // 9.【Outbox】仍在本 transaction；失敗會連同上述寫入一起 rollback。
    publish(result);
    return result;
}

公開方法只保留九個有順序意義的階段；lock、validation、mutation 與 result assembly 的細節各自放在具名方法或 StockOperationAssignmentResultFactory。若 Quant 不存在、已過期、ATP 不足或版本改變，Proposal 仍會被判 stale 並完整 rollback。

06 · Port / Adapter / Persistence

Application Store 怎麼分工？

Inventory 的自訂資料 Port 全由 Application 擁有、統一使用 *Store，並放在 capability 的中性 application.port。同一 canonical model 的普通讀取、lock 與寫入合在一個 cohesive Store；Candidate、Supply 與 visibility projection 仍維持 focused Store，避免重新長成巨大 Repository。Domain 不宣告 persistence port。

07 · Outcomes & Failure Semantics

不是每次呼叫都會配到貨

「沒有 assigned result」可能是正常等待，也可能是資料衝突。這些結果不能用同一個模糊的 false 解讀。

完整成功

所有 SKU 足夠且 proposal 在鎖內仍有效。Operation／Moves → ASSIGNED，建立 MoveLines，增加 Quant reserved，寫 Outbox，transaction commit。

正常等待：有 predecessor

已註冊的 Operation／Moves 保持 CONFIRMED；不讀 supply、不產生 proposal、不改 Quant。等前單離隊後由 wake pipeline 再試。

正常等待：供給不足

Planner 產生 insufficient proposal，沒有任何 partial reservation。Operation／Moves 保持 CONFIRMED，等待 inventory availability event。

來源不存在／已取消

Source adapter 回 empty，Use Case 正常結束，不建立 movement。在事件模式下 Inbox claim 會隨 transaction commit，表示該事件已被處理。

Registration replay

同一 source 已存在且不可變內容相同時重用既有資料。事件模式通常更早就由 Inbox 擋住同一 event；Registrar 保護的是 source-level idempotency。

資料衝突／stale proposal

相同 source 內容不同會拋 conflict；版本、ATP、效期或 predecessor 在規劃後改變會拋 stale。例外向外傳遞，整個 transaction rollback；訊息基礎設施可重試。
