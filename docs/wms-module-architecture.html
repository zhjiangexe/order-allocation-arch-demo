一、模組與責任邊界

先穩定 WMS 自己的 commands、aggregate rules 與 committed events，再由未來 adapter 接 REST、Kafka、JPA、Inventory 或 TMS。

wms.outbound

Wave planning／release，以及 Warehouse Shipment 的揀貨、打包、待派運、交接與取消決策。

  • Aggregates：Wave、Shipment
  • Repository ports：WaveRepository、ShipmentRepository
  • 9 個 command use cases

wms.inbound

一張 Inbound Operation 的登記、到貨、驗收、隔離與上架完成。

  • Aggregate：InboundOperation
  • Repository port：InboundOperationRepository
  • 4 個 command use cases

Adapters / Infrastructure

共用 messaging 已拆成 API／Events、Outbox producer、Inbox consumer、Kafka consumer、Spring Boot auto-configuration 與薄 starter；platform-infrastructure 不再負責 messaging wiring。WMS 專屬 repository implementation、consumer 與外部系統 mapping 仍刻意未建立，且 wms core 不反向依賴它們。

依賴方向

未來 WMS Adapter → WMS Usecase → Aggregate → Domain Event；runtime adapter 可依賴 contracts 與 messaging:*，WMS core 只宣告 ports。Messaging adapter 可以依賴 API 與契約，但不得反向依賴 WMS domain。

二、Outbound 正常流程

Wave 先選擇多張 Shipment；Release 時才建立 WarehouseWork／PickTasks。Wave 與單張 Shipment 各有生命週期，不以全 Wave 完成阻塞已揀完的單張 Shipment。

CreateShipmentUsecaseCREATED · 只建立 demand lines
→
PlanWaveUsecaseWAVE_PLANNED · claim Shipment
→
ReleaseWaveUsecase建立 WarehouseWork／PickTasks
→
ConfirmPickUsecasePICKING → PICKED
→
PackShipmentUsecasePACKED
→
StageShipmentUsecaseREADY_FOR_DISPATCH
→
HandOverShipmentUsecaseHANDED_OVER_TO_CARRIER

並行的 Wave checkpoint：PlanWaveUsecase → ReleaseWaveUsecase → CompleteWaveUsecase。只有所有 assignment 的 picking work 完成或取消才關閉 Wave；某張 Shipment 一旦 PICKED，即使同 Wave 仍有工作，也可先 Pack。ShipmentReadyForDispatch 是未來交給 dispatch／TMS 的粗粒度 readiness fact。

Wave 第一版刻意展示的實作切面

切面目前做法維護界線
演算法PriorityCapacityWavePlanner 先過濾 Facility／cutoff，再依 priority、dispatch deadline、created time、Shipment ID 穩定排序，最後 greedy 填入 Shipment／line／unit 容量。結果可重現、容易解釋；暫不導入 knapsack、route optimization 或 AI optimizer。
資料結構不可變 WaveCandidate／WaveAssignment snapshots、排序 List、重複檢查 HashSet、claim 時以 ID Map 對回 aggregate。只保存規劃所需資料；Wave 若成長到數千張，再把 assignments 改為分頁 persistence。
設計模式WavePlanner Strategy、Wave／Shipment Aggregates、Repository ports、Domain Events，以及 command redelivery idempotency。演算法可替換，但不把 repository、Kafka、排程或 WES 細節塞進 domain model。
工作產生Planning 只 claim Shipment；Release 才建立 WarehouseWork 與逐 line PickTask。避免候選重算時提前產生現場工作；未來真的採 zone／cluster picking 再拆 work ownership。

三、取消依實體進度分支

CancelShipmentUsecase 不假裝所有狀態都能立即 rollback；Aggregate 回傳 typed CancellationOutcome。

CREATED / WAVE_PLANNED / RELEASED

Wave 尚未 release 時沒有 PickTask；已 release 但未開工時取消 WarehouseWork，進入 CANCELLED。

已開始實體作業

進入 CANCELLING，發布 ShipmentPutbackRequired；Putback lifecycle 尚待實作。

已交給 Carrier

不再作 WMS cancellation，發布 ShipmentCancellationRejected；後續應由 return／TMS 流程處理。

七、刻意未實作與下一步

先補 source of truth 與現場行為，不先建立新的 workflow module。

缺口目前狀態建議
Repository／Outbox implementationsWMS wiring 未建立通用 Outbox producer 已在 messaging:messaging-producer-outbox；WMS repository adapter、event translator 與 runtime composition 仍待建立，不放回 domain package。
Order Promising → WMS input上游待補目前 OrderAllocatedIntegrationEvent 只有 orderId／allocatedAt。order-promising integration snapshot 尚需準備 allocation／StockPicking ID、owner、Facility、committed line／move／source location／quantity、dispatchBy 與 releasePriority；整單取消也需保留 order-to-shipment correlation。各缺口已直接註解在 CreateShipmentCommand／CancelShipmentCommand 上。
Inventory adapter未建立以 committed receipt／putaway／handover facts 接庫存帳，不讓 WMS aggregate 直接依賴 order-promising model。
Short-pick resolution／Putback僅有事件先建 WMS commands、business keys 與 terminal outcomes。
Wave planning／releaseCore 已建立目前依 priority、dispatch cutoff、Shipment／line／unit capacity 選擇；取消的 assignment 保留 audit trail，但不產生 WarehouseWork。template persistence 與 scheduler 尚未建立。
Replenishment、Pick route、Container／LPN、Loading未建立依真實倉庫需求逐一形成 process；不要預先建立空殼。
Temporal orchestration不採用只有跨獨立系統的 durable coordination 成立後，依 ADR 重新評估。
