一、模組與責任邊界

WMS core 穩定 commands、aggregate rules 與 committed events；同一 bounded-context module 提供跨邊界 transport 與 persistence adapters。

wms.outbound

Wave planning／release，以及 Warehouse Shipment 的揀貨、打包、待派運、交接與取消決策。

  • Aggregates：Wave、Shipment
  • Repository ports：WaveRepository、ShipmentRepository
  • 9 個 command use cases

wms.inbound

一張 Inbound Operation 的登記、到貨、驗收、隔離與上架完成。

  • Aggregate：InboundOperation
  • Repository port：InboundOperationRepository
  • 4 個 command use cases

deployments:monolith → wms-context

單體以同一組 messaging starter 接收 OrderAllocationCommittedIntegrationEvent。Events mode 由 consumer 建立 Shipment；Temporal mode 則由 Workflow Activity 呼叫相同的 CreateShipmentUsecase。Handover 透過通用 IntegrationEventPublisher 寫入 transactional Outbox。

依賴方向

deployments:monolith → wms-context → application API → aggregate → repository ports；messaging、Temporal Activity 與 JPA adapters 都由外向內呼叫。其他 context 只交換 integration-contracts 的不可變 snapshot，不引用 WMS aggregate，也不跨 boundary 讀取 WMS tables。

二、Outbound 正常流程

Wave 先選擇多張 Shipment；Release 時才建立 WarehouseWork／PickTasks。Wave 與單張 Shipment 各有生命週期，不以全 Wave 完成阻塞已揀完的單張 Shipment。

CreateShipmentUsecaseCREATED · 只建立 demand lines
→
PlanWaveUsecaseWAVE_PLANNED · claim Shipment
→
ReleaseWaveUsecase建立 WarehouseWork／PickTasks
→
ConfirmPickUsecasePICKING → PICKED
→
PackShipmentUsecasePACKED
→
StageShipmentUsecaseREADY_FOR_DISPATCH
→
HandOverShipmentUsecaseHANDED_OVER_TO_CARRIER

並行的 Wave checkpoint：PlanWaveUsecase → ReleaseWaveUsecase → CompleteWaveUsecase。只有所有 assignment 的 picking work 完成或取消才關閉 Wave；某張 Shipment 一旦 PICKED，即使同 Wave 仍有工作，也可先 Pack。跨 context 的 WMS terminal facts 為 ShipmentHandedOverIntegrationEvent 與 ShipmentCancelledIntegrationEvent。

Wave 第一版刻意展示的實作切面

切面目前做法維護界線
演算法PriorityCapacityWavePlanner 先過濾 Facility／cutoff，再依 priority、dispatch deadline、created time、Shipment ID 穩定排序，最後 greedy 填入 Shipment／line／unit 容量。結果可重現、容易解釋；暫不導入 knapsack、route optimization 或 AI optimizer。
資料結構不可變 WaveCandidate／WaveAssignment snapshots、排序 List、重複檢查 HashSet、claim 時以 ID Map 對回 aggregate。只保存規劃所需資料；Wave 若成長到數千張，再把 assignments 改為分頁 persistence。
設計模式WavePlanner Strategy、Wave／Shipment Aggregates、Repository ports、application publication factory，以及 command redelivery idempotency。演算法可替換；Domain 不依賴 Kafka、Outbox、Temporal、排程或 WES。
工作產生Planning 只 claim Shipment；Release 才建立 WarehouseWork 與逐 line PickTask。避免候選重算時提前產生現場工作；未來真的採 zone／cluster picking 再拆 work ownership。

三、取消依實體進度分支

CancelShipmentUsecase 不假裝 command 已提交就等於物理終態；command 回傳 typed CancelShipmentStatus，生命週期另由 ShipmentCancellationState 表達。

CREATED / WAVE_PLANNED / RELEASED

Wave 尚未 release 時沒有 PickTask；已 release 但未開工時取消 WarehouseWork，進入 CANCELLED。

已開始實體作業

回傳 ACCEPTED 並進入 CANCELLING／REQUESTED；recovery 完成後才發布 ShipmentCancelledIntegrationEvent。

已交給 Carrier

回傳 REJECTED；Order 保持完成狀態，後續應由 return／TMS 流程處理。

七、刻意未實作與下一步

現行主線已接通；下一步是用真實現場入口替換 simulation，並補足異常與進階作業。

缺口目前狀態建議
Repository／Outbox implementations主線已建立InboundOperation、Wave、Shipment 均有 JPA adapter；handover 經 ShipmentHandedOverPublicationFactory → IntegrationEventPublisher → Outbox 發布。
Allocation → WMS input雙模式已接通唯一的 OrderAllocationCommittedIntegrationEvent 由 Events consumer 或 Temporal Signal／Activity 其中一條路徑建立同一個 Shipment。
Inventory completion已接通ShipmentHandedOverIntegrationEvent 在 Events mode 直接觸發 CompleteOutboundMovementsUsecase；Temporal mode 由 Workflow Activity 呼叫相同 use case。
Short-pick resolution／真實 Putback tasks部分模擬目前已有 durable CANCELLING backlog 與 cancellation completion event；但尚未建立 PutbackTask、庫位建議與人工確認模型。
Wave planning／releaseCore + persistence 已建立目前 simulation 在單一 transaction 內規劃、release 並完成一張 Shipment；真實 Wave scheduler／operator entrypoint 尚未接入。
Replenishment、Pick route、Container／LPN、Loading未建立依真實倉庫需求逐一形成 process；不要預先建立空殼。
Temporal orchestration可選模式TemporalWmsActivitiesAdapter 委派既有 WMS use cases；Workflow 只保存跨 context checkpoints，不接管 Pick／Pack／Stage 內部狀態。
