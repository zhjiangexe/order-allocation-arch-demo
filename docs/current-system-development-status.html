一、端到端流程總覽

流程依「操作準備 → 收貨／接單 → 配置結果 → 缺貨重配 → 查詢 → 取消」閱讀；收貨與接單可各自獨立發生。

16 / 16 use cases Catalog 5 個、Ordering 6 個、Stock 5 個。流程圖不再用「5 個 queries」或「RecordOrder…」縮寫，每一個 use case 都會具名出現。

選擇作業範圍

先取得貨主，再依頁面需要展開商品、SKU、Facility、內部庫位與現有庫存。

  • Owner → Product → SKU
  • Owner → Facility → Location
  • Location → StockPool
  • 純讀取，不發布事件

確認收貨

在單一交易建立 inbound movement、完成批次明細並增加實體庫存。

  • ConfirmStockReceiptUsecase
  • 提交可用庫存增加事實
  • Kafka 快速喚醒等待需求

接單與初次配置

訂單先落地為 PENDING，再由 Stock context 建立 outbound movement 並配置。

  • PlaceOrderUsecase
  • AllocateOrderUsecase
  • 整單 ALLOCATED 或 BACKORDERED

回寫、重配與查詢

Ordering 接收配置結果；缺貨單在庫存增加或排程掃描時重配，畫面再主動刷新。

  • RecordOrderAllocationUsecase
  • RecordOrderBackorderUsecase
  • AllocateWaitingDemandUsecase
  • ListRecentOrdersUsecase／GetOrderUsecase

取消與釋放

取消訂單後發布事件，Stock context 取消搬運並歸還鎖定量。

  • CancelOrderUsecase 尚無入口
  • CancelMovementsUsecase 已可消費事件
  • 釋放後主動 wake 尚未實作

五、開發成熟度與缺口

「16 個 use case 都有列到」不等於「所有倉儲能力都已完成」；目前最成熟的是接單、promising 與庫存交易邊界。

已完成／已有測試保護

  • Catalog 查詢鏈可提供貨主、商品、SKU、Facility 與 internal location。
  • 前端可查位置批次庫存、建立多品項訂單並同步確認收貨。
  • 收貨建立 inbound picking、move、move line，再增加 StockPool。
  • 初次配置與 backorder wake 共用 FIFO／FEFO／whole-order 語意。
  • 配置／缺貨結果由各自的 projection use case 回寫 Ordering。
  • Inbox、Outbox、Kafka retry、DLT、reconciliation scheduler 與相關測試已存在。

已有骨架，但仍是簡化版

  • CancelOrderUsecase 與取消事件鏈已實作，但沒有 REST／UI／上游訊息入口。
  • Inbound 是直接確認完成的一段式流程，尚無 ASN、卸貨、驗收、上架 checkpoint。
  • Outbound 目前做到 demand、picking／moves 與配置，尚未形成完整揀貨執行鏈。
  • Scheduler 可收斂等待佇列，但缺少等待年齡、失敗率、每輪量等營運觀測。
  • 庫存批以入庫日與效期識別，尚未擴充 lot／serial／container。

尚未形成 use case 的主要能力

  • Outbound execution：pick、pack、stage、ship 與操作人員工作佇列。
  • 出庫完成後正式扣減 on-hand 的 shipment posting use case。
  • 取消釋放庫存後主動喚醒舊 backorders。
  • 盤點、庫存調整、報廢、移庫與對帳。
  • 多段 inbound route／putaway policy 與中繼責任位置。
  • 完整授權、主檔維護、營運監控與 migration／rollback 策略。

六、交易與 Context 邊界

切分點不是「每個方法都變 use case」，而是每個可獨立提交、重試、等待或投影的 checkpoint。

邊界現在的做法理由
Receipt → StockPoolConfirmStockReceiptUsecase 同交易 invoke recorder 與 completer。picking、move line 與實體庫存必須一起成功或一起 rollback。
Receipt → Backorder提交 StockAvailabilityIncreased，由 Kafka 另開交易。收貨成立後不應因 outbound queue 失敗而撤銷。
Ordering → StockOrderPlaced 啟動 AllocateOrderUsecase。Ordering 只擁有需求；Stock 擁有配置與搬運事實。
Stock → Ordering兩個 record use cases 各自消費 allocated／backordered facts。訂單狀態是落後投影，不拿來當 Stock 的配置閘門。
Kafka → Scheduler兩個 adapter 共用 AllocateWaitingDemandUsecase。Kafka 提供速度，Scheduler 提供最終收斂；政策只有一份。
Cancel compensationOrdering 先取消並提交事件，Stock 再取消 movements。兩個 context 各自提交，重送由 Inbox 與 domain idempotency 吸收。
Use case → ComponentsRecorder、Assigner、Completer、Canceller 不獨立開交易。它們是可重用 application policy，不是獨立流程 checkpoint。

七、建議後續實作順序

先補目前流程真正中斷的位置，再延伸至完整倉儲 execution。

接通取消入口

替 CancelOrderUsecase 增加 REST／UI 或明確上游訊息入口，補上 16 個 use case 中唯一不可達的一個。

補釋放後 wake

取消 movements 歸還可用量後發布 availability fact，讓較舊 backorders 不必只等排程。

完成 outbound execution

從 ASSIGNED move 往下建立 pick／pack／stage／ship checkpoint，並定義正式扣減 on-hand 的 use case。

穩定 WMS 業務邊界

先定義 picking、packing、dispatch preparation 與 recovery 的 identity、commands、events 與 terminal outcomes，再判斷是否真的需要跨系統 orchestration。
