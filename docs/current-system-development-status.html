一、端到端流程總覽

流程依「操作準備 → 接單與配貨 → WMS 執行 → 出庫與完成 → 取消」閱讀；每個跨 context checkpoint 都由已提交的 Integration Event 或 Temporal Activity 推進。

35 個 use cases · 3 個業務 contexts + 1 個主檔 context Logistics Data、Ordering、Inventory、WMS 各自擁有 model 與 transaction；Temporal runtime 是跨 context coordinator，不是新的資料 owner。

選擇作業範圍

先取得貨主，再依頁面需要展開商品、SKU、Facility、內部庫位與現有庫存。

  • Owner → Product → SKU
  • Owner → Facility → Location
  • Location → StockQuant
  • 純讀取，不發布事件

確認收貨

在單一交易建立 inbound movement、完成批次明細並增加實體庫存。

  • ConfirmStockReceiptUsecase
  • 提交可用庫存增加事實
  • Kafka 快速喚醒等待需求

接單與初次配置

訂單先落地為 PENDING；Events consumer 或 Temporal Activity 其中一條路徑建立 immutable demand 並嘗試 ship-complete 配置。

  • PlaceOrderUsecase
  • AllocateOrderUsecase
  • Demand 整單 ALLOCATED 或保持 PENDING

重配與履約

缺貨 demand 由 availability event 低延遲喚醒，scheduler 公平補漏；成功後同一事件分別推進 Ordering projection 與選定的 fulfillment driver。

  • RecordOrderAllocationUsecase
  • PendingDemandAllocationUsecase
  • PendingDemandBacklogAllocationUsecase
  • Shipment → Handover → Outbound completion

取消與釋放

共用 REST API 依 mode 選擇同步 coordinator 或 Workflow Update；Order 安全取消後再由事件清理 Inventory。

  • POST /orders/{id}/cancellation-requests
  • Events／Temporal 各有唯一 coordinator
  • CancelMovementsUsecase 已可消費事件

五、開發成熟度與缺口

Order fulfillment 主線已可在 Events／Temporal 兩種模式完成；尚未完成的是外部 WMS 現場入口與部分進階倉儲能力。

已完成／已有測試保護

  • Catalog 查詢鏈可提供貨主、商品、SKU、Facility 與 internal location。
  • 前端可查位置批次庫存、建立多品項訂單並同步確認收貨。
  • 收貨建立 inbound picking、move、move line，再增加 StockQuant。
  • 初次配置與 pending-demand wake 共用 FIFO／FEFO／ship-complete 語意。
  • 單一 allocation event 同時供 Ordering projection 與 mode-selected fulfillment driver 使用。
  • Shipment、Wave、Pick、Pack、Stage、Handover、正式出庫扣帳與 Order FULFILLED 已接通。
  • Pure JDBC Inbox／Outbox、Debezium、Kafka、Temporal、retry、DLT、observability 與 reconciliation scheduler 已存在。
  • 17 條 Karate E2E 會實際啟動 Spring Boot、PostgreSQL、Kafka、Connect 與 Temporal Server。

已有骨架，但仍是簡化版

  • 取消 REST 與兩種 coordinator 已實作；已開工 Shipment 的 putback recovery completion 尚未實作。
  • WMS Inbound 有 register、arrival、inspection、putaway checkpoints，但尚未接入正式外部 entrypoint。
  • Outbound 倉內步驟目前由 simulation scheduler 自動完成，不是人員、設備或外部 WMS 分段命令。
  • Scheduler 可收斂等待佇列，但缺少等待年齡、失敗率、每輪量等營運觀測。
  • 庫存批以入庫日與效期識別，尚未擴充 lot／serial／container。

尚未形成 use case 的主要能力

  • 真實 WMS／scanner／設備入口與操作人員工作佇列。
  • Putback recovery、short-pick resolution 與人工介入流程。
  • CancelAllocationDemandUsecase 的正式 source-agnostic caller。
  • 盤點、庫存調整、報廢、移庫與對帳。
  • 多段 inbound route／putaway policy 與中繼責任位置。
  • 完整授權、主檔維護、營運監控與 migration／rollback 策略。

六、交易與 Context 邊界

切分點不是「每個方法都變 use case」，而是每個可獨立提交、重試、等待或投影的 checkpoint。

邊界現在的做法理由
Receipt → StockQuantConfirmStockReceiptUsecase 同交易 invoke recorder 與 completer。picking、move line 與實體庫存必須一起成功或一起 rollback。
Receipt → Pending demand提交 StockAvailabilityIncreasedIntegrationEvent，由 Kafka 另開 attempt transaction。收貨成立後不應因 outbound queue 失敗而撤銷。
Ordering → InventoryOrderPlacedIntegrationEvent 由 Events consumer 或 Temporal Activity 其中一條路徑呼叫 AllocateOrderUsecase。Producer 不知道 orchestration mode；Ordering 只擁有訂單需求。
Inventory → Ordering / WMS單一 OrderAllocationCommittedIntegrationEvent 分別供 Ordering projection 與 fulfillment driver 消費。一個已提交事實可以有多個讀者，不為 driver 複製 producer event。
Kafka → SchedulerAvailability consumer 與 backlog scheduler 都呼叫 PendingDemandAllocationUsecase；scheduler 外層另由 PendingDemandBacklogAllocationUsecase 管公平輪次。Kafka 提供速度，Scheduler 提供最終收斂；單筆 attempt 政策只有一份。
WMS → Inventory → OrderingHandover event 推進 CompleteOutboundMovementsUsecase，再由 event consumer 或 Temporal Activity 完成 Order。庫存只在 custody handover 後正式扣帳；兩種 mode 共用 use case。
Cancel compensationREST coordinator 先取得 WMS safe decision，再取消 Order；OrderCancelledIntegrationEvent 非同步清理 Inventory。不在實體作業不可逆後假裝 rollback，重送由 request identity、Inbox 與 domain idempotency 吸收。
Use case → ComponentsRegistrar、Selection、Planner、Committer、Completer、Canceller 不自行成為跨 context driver。它們是 transaction 內 application／domain policy，不是獨立 orchestration checkpoint。

七、建議後續實作順序

主線已接通；後續優先替換模擬入口並補真正尚缺的異常處理。

替換 WMS simulation

以操作 API、scanner、設備或外部 WMS adapter 分段呼叫既有 Wave／Pick／Pack／Stage／Handover use cases。

完成 recovery

替 PUTBACK_REQUIRED 建立可持續、可觀測的實體回架與 cancellation completion。

建立 fulfillment projection

將 Demo query 的跨 context 即時組裝改成事件驅動 read model，降低查詢時耦合。

補 production operations

建立等待年齡、scheduler run、Temporal execution、Inbox／Outbox lag、DLT 與 connector health 的營運視圖。
